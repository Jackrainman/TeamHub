# 差异化在场排班 — 表现形式重定向 + 资源领域模型（定稿）

> 承接 D-029（`derivePresenceSchedule` 派生纯函数）+ D-069（课表→组级容量、排班接出 `SchedulePage` 卡片版）。
> 本文解决两件事：① 排班「画给人看」的形态；② 系统里「车」这个实体建得太简陋，装不下「按赛季换车 + 生命周期 + 拆件血缘」。
>
> **红线复述（全文每处自检，AGENTS §2 I0/C2/A1）**：派生输出主键只能是 group / resource / task，**绝无 memberId 维度、绝无个人出勤 / 时长聚合**；AI 不替人拍板、人在环；派生优先（用着就更新）；小作坊轻量、比死表格更省事。**特别地（定稿新增）**：在场排班的语义是「接力顺序里此刻轮到谁、谁可以下班 / 不用加班」——是**给人正名、帮人省事**（告诉你这阶段没你事、可以走），不是「停谁的活」、更不是盯出勤（守 A1）。

## 1. 组织结构（先立，影响全局）— 决定 G、L

- **任务分配的基本单元 = 四个组**：电控、视觉、机械、电路。**设置页可增减**（目前就这四个）。
- **删除「程序组」作为领任务单元**。「程序 = 电控 + 视觉」**只保留为汇报 / 过载向上合并的视角**——看「程序口径整体过载没有」时把电控 + 视觉合起来看，但它**不直接领任务、不在排班里作为独立单元出现**。
- **总联调 = 所有组都必须各到至少一人**（不挂某一个组）。它是一个特殊的收敛任务：在场要求是「每个组至少一人」，而非「挂在某组下」。
- **现状核对**：`fixtures.ts` 组树本身正确（机械 / 电路顶层，叶子组挂电控 / 视觉等）。唯一遗留 = `grp-program` 仍**直接持有** `t-r1-integration` / `t-r2-integration` 并有自己的成员 `m-progA`/`m-progB`。**下一轮实现时调和**：① 两个程序成员按实际职责归口到电控 / 视觉；② 总联调改「全组各一人」语义；③ `grp-program` 去掉「领任务」身份、只留汇报视角。本轮不改 fixtures。
- **落地**：组织结构规则写进 `AGENTS.md §1`（删程序组领任务、留汇报视角、总联调全组各一人随本轮同步）。

## 2. 表现形式：两视图 — 决定 A、I、J、M

用户的核心洞察：**按用途分图，且去掉那张画不出东西的甘特**。

### 2.1 全局视图：依赖流程图（总图）

已有 `DepGraphPage`，保持现役角色：全局看「整盘棋怎么走、谁卡谁」，**「不知道未来怎么走的时候看」**。
*可选增强*：在节点上叠「当前态」颜色（轮到谁 = 蓝描边、待命 = 橙描边、这阶段没事 = 变灰）——列为可选，主力短期视图交给接力链。

> **甘特图：砍掉**（定稿决定 A）。理由：① 比依赖图更难一眼看懂「谁卡谁」；② 系统数据真相层**没有「每件事做多久 / 何时截止」**（只有赛季起止），硬画甘特要么逼大家填工期（撞「别让人记过去 / 别建死表」的小作坊铁律），要么退化成赛季两端点的空轴。**项目进度仍由依赖流程图承载**。故 D-041「甘特暂缓」继续生效，本轮不再引入工期 / dueDate、无需对账。

### 2.2 短期 / 操作视图：接力顺序链（主推，多车并排）

把今晚 / 明天每台车的**接力顺序**画成一条编号链，**只表先后、不表钟点**（直接渲染现有的 `orderInWindow`，彻底不碰时间戳）。

**语义重定（定稿核心）**：这张图回答「**接力顺序里此刻轮到谁、谁可以下班 / 不用加班**」，**不是「停谁的活」**。典型工序：

```
今晚（顺序，非钟点）                 支持多车并排：

26R1  ①机械修 ▸ ②电控+电路调 ▸ ③视觉    26R1  ①机械 ▸ ②电控+电路 ▸ ③视觉
      轮到了    待命/快轮到    这阶段没事  26R2  ①机械 ▸ ②电控
                                              轮到了   待命
```

- 一台车可能只坏一个机构，但活儿是**接力**干的：先机械修，修完电控 + 电路调，再到视觉；机械、视觉各自干完就**可下班**。系统帮人省事的点在于告诉他「**你这阶段干完了 / 还没轮到你，不用在这儿耗着**」。
- 三态映射到接力位置：**此刻轮到（在场）/ 快轮到、待命（随叫）/ 这阶段没你事或已干完可走（可不来 →「可下班」）**。
- 可叠 D-069 的容量读数 `feasibility`（充裕 / 偏紧 / 冲突）当小徽章——那是**组级整数**派生，无任何人维度。
- **多车并排：要做**（决定 M）——一晚不同人调多台车是常事；窗宽不够时的折叠 / 滚动留实现期按屏宽定（见 §6）。

**现有卡片网格（`SchedulePage`）降级**：作为接力链点开后的详情，或窄屏退化态；被卡组的「可看资料」收在这里。

### 2.3 加车交互（决定 I、J）

- **排班里的车手动加**；demo 先放两辆：**26R1、26R2**（2026 赛季）。
- 加车的交互形态（右上角「加」按钮逐个加 vs 侧边栏拖拽）= **最后的 GUI 优化，先放最后**。先用最简单的右上角加 / 手填即可。

### 2.4 红线自检

两视图的节点都是「任务 / 组 / 车」，颜色来自接力位置 / 容量派生；没有任何「按人横向计时」的条。「某人这周在场多久」——两视图都答不出。且「谁可下班」是帮助语气、私下回本人，不上报、不排名。✅
> 落实现纪律（下一轮）：接力链只读 `/api/schedule` 的**组键派生**、不外露原始 session 的 `invitedMemberIds`；此约束下一轮**升为结构约束**（schema 形状 + 读视图 omit），不止于本文散文。

## 3. 资源领域模型：车 = 带编号对象（单层）+ 状态 + 零件拆装 — 决定 B、C、D、E、F、H、K

### 3.1 现状三处缺口（`governance.ts` `SharedResource`）

现在「车」只是一条记录：`{ robotTarget: R1|R2|shared, status: available|inUse|down|upgrading, ... }`。缺：
1. **分不清赛季**——`Season` 存在、`Project` 有 `seasonId`，但 `SharedResource` 没赛季外键；只有「1 号车」，区分不了 25R1 / 27R1。
2. **状态太少**——没有「维修 / 退役 / 拆解」。
3. **零件来历为零**——「25R1 的电机装到 27R1」无处可记；`InvStore` 是空接口。

### 3.2 单层「车 = 带编号对象」（决定 B、K）—— 取消车位两层

定稿放弃「车位（RobotSlot）+ 具体车（RobotInstance）」两层抽象（评审指出两层与现役级联算法脱节、且 RobotSlot 绑单赛季 Project 自相矛盾；用户拍板**取消车位层**）。改为：

- **车 = 一个独立对象**，跨赛季各台永久并存可查（25R1 退役了，27R1 还要能查它继承了什么）。
- **编号（displayCode）派生生成、禁手写**：`赛季后两位 + 位置 (+ 版本)`，如 `25R1` / `26R1-v2`。「位置」（R1 / R2）只是编号的一部分，不再是独立实体层。
- **每个（赛季, 位置）最终只剩一台活跃车**且固定不变（25R1 / 26R1）——这条用户拍板的事实，正好让排班直接挂在车对象上、无需「车位 → 具体车」的中间映射，化解了评审里那个「按车位枚举 vs 按具体车」对不上的「落地必爆」冲突。
- **版本 `v`（决定 K）= 第几代整车**：同赛季同位置若旧车整车全拆重做，第二台 = `26R1-v2`；默认 `v1`；升 `v` 的频率极低（一赛季顶多一次）。`v` 同时充当「同赛季同位置撞名」的区分位。

### 3.3 状态：宏观「维修」态 + 可选注释（决定 C）—— 不精确到机构

```
可用 ──▶ 使用中
  ▲         │
  │      （撞坏/要修）──▶ 维修中 ──修好──▶ 可用
  │                                         │
  └────────────────（手动）退役 ◀───────────┘
                         │
                         ├─ 整车留展示
                         └─ 拆一部分 ──▶ 拆解（半留）
```

- **宏观状态集小**：可用 / 使用中 / 维修中 / 退役 / 拆解（拆一半）。**「维修」是一个宏观态，不精确到「哪个机构坏了」**；需要说明时**附一条自由注释**（如「撞坏底盘」「电控板烧了」）即可。
- **退役 = 人手动设**，不自动推（守「AI 不拍板」）。退役后可**整车留展示**或**拆一部分**（拆解态）。
- **工序先后由排班层承载**：先机械后电控这种接力顺序，是**人在排班窗里排的 `orderInWindow`**，**不从车状态自动推**。车状态只回答「这台车现在能不能上 / 在不在修」。
- 车不可上（维修 / 退役 / 拆解）→ 下游接力据此提示「此刻不用来 / 可下班」（接力释放语义，非「停活」）。现役 `resourceDown` 分支下一轮升级为读「该状态能否上车」+ 接力释放，挂在车对象上、不再走车位枚举对齐。
- 实现倾向「枚举状态 + 一张行为对照表」（哪个状态能不能排班 / 显不显示 / 要不要告警），不上重型状态机库。

### 3.4 零件血缘 + 库存总表（决定 D、E、F）

**「25R1 拆 → 27R1」记成两条动作**（对话记账级，队员一句话、助手代记）：
1. 「把 25R1 的某电机拆下」→ 该零件回到闲置池（货架）。
2. 「把它装到 27R1」→ 该零件现属 27R1。
- **关键**：拆件时绝不「删零件再新建」，否则丢掉来历；永远是「拆下」动作让归属变空，零件本身不删。

**粒度（决定 D）**：**绝大多数零件按数量记**；只有 1~2 个的、和重要的（电机 / 电调 / 主控）才**手动标记**单独追踪个体 + 血缘。

**录入路径（决定 E）**：**初始只录闲置零件数量**；**每台车装了多少后续再补**（智能体调接口 / 手动）。

**库存总表（决定 F）**——回答「闲置多少 / 每台车预留 / 已有多少」：
```
零件          闲置(货架)   25R1   26R1   26R2   27R1(预留)
GM6020 电机       3          2      4      0      6
C620   电调       5          2      4      0      6
主控板            1          1      1      0      1
```
- **「预留」（定稿决定 F）= 已经从仓库拿出来、不在货架、禁止他用、记在该车上**——即**从闲置池扣减、归到该车那一列**。`闲置数 = 总数 − 各车已用(含预留)`。
- **不写「在造」列**。
- 退役车若拆，拆下的零件**归还货架后才可再用**（从该车列挪回闲置列）。
- 拆下的零件进库存总表、不进任务总图（任务总图只画活儿的依赖）。

> 这套「零件类型 + 零件个体（仅追踪件）+ 拆装动作 + 数量账」正好是第三支柱**库存 / BOM**（`INV-BOM-DESIGN`）的最小内核——血缘讨论顺手把库存地基摸出来了。**本轮不落代码**；下一轮是否落库存最小内核见 §7（库存仍排在后面）。

### 3.5 车 ↔ 库存互联兜底（决定 H）

两套数据靠「这颗零件 / 这批数量现属哪台车」打通。**互联出问题时**（数量对不上、血缘断链、孤儿零件）→ **让智能体发消息（走 Hermes / 飞书触点）+ 查问题根源**，而不是默默吞掉或硬卡。对接 `HUB-HERMES-ADAPTER`（仍 gated，触点接通前此条只能 mock）。

### 3.6 红线自检

零件、拆装动作、数量账的主键都是物 / 事；记录人只到「谁录的」这种来源（actor），**不做「谁拆了多少件」的人维度统计**，**库存数量账绝不与在场态按人 join**。✅（同 §2.4，下一轮落实现前升为结构约束）

## 4. 工作流抽象 + 规范

**两个时间维度（长期主轴 / 短期运行）**（注：与 §3.2 已废止的「车位 + 具体车」车模型分层无关，此处指时间尺度）：
- **长期主轴层**（赛季尺度，主键 = 具体某台车对象）：可用 → 使用中 → 调试 / 比赛 → 赛后拆件 → 下赛季重建。
- **短期运行层**（今晚 / 本周，主键 = 组）：在场排班（接力顺序），挂在主轴「当前可用的车」上。覆在长期图上的一层薄运行态，不是独立日历。

**该标准化（少数硬规则）**：车 `displayCode` 派生生成（含 `v` 代次，禁手写）；状态迁移走写入白名单（沿 `GovStore` 白名单），AI 只出建议、人确认才落；拆件固定记两条动作、备注（自由注释）按需，记错用「修正」动作不删历史；**改资源状态 / 拆装动作前先回显该车当前态、供人确认再写**（前端展示现值，沿用户「改动前先说清现状再改」诉求）。

**该保持轻量（守 P13 别建没人填的死表格）**：不强制录设计图纸级 BOM（留 CAD，用到时挂模板）；不强制每颗螺丝编号（只追踪贵重件）；排班不强制提前排满（谁在推就标谁，是建议草稿不是考勤表）；在场不引钟点；**车状态不精确到机构、只一个宏观维修态 + 可选注释**。
