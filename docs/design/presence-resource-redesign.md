# 差异化在场排班 — 表现形式重定向 + 资源领域模型

> 承接 D-029（`derivePresenceSchedule` 派生纯函数）+ D-069（课表→组级容量、排班接出 `SchedulePage` 卡片版）。
> 本文解决两件事：① 排班「画给人看」的形态（现状卡片网格有待商榷）；② 系统里「车」这个实体建得太简陋，装不下「按赛季换车 + 生命周期 + 拆件血缘」。
>
> **红线复述（全文每处自检，AGENTS §2 I0/C2/A1）**：派生输出主键只能是 group / resource / task，**绝无 memberId 维度、绝无个人出勤 / 时长聚合**；AI 不替人拍板、人在环；派生优先（用着就更新）；小作坊轻量、比死表格更省事。

## 1. 组织结构（先立，影响全局）— 决定 G

- **任务分配的基本单元 = 四个组**：电控、视觉、机械、电路。**可在设置页增减**（目前就这四个）。
- **「程序组」是抽象大组**，= 电控 + 视觉之和，不直接领任务，用于「汇报 / 过载」向上合并。
- **现状核对（重要）**：`fixtures.ts` 的组树**已经是对的**——`grp-mech`/`grp-circuit` 顶层，`grp-program`(程序) 顶层且 `parentGroupId` 指向它的有 `grp-ec`(电控)/`grp-vision`(视觉)；普通任务（机械臂装配 / 电路板 / 底盘 / 视觉数据流）也确实只挂在四个叶子组上。「出入」只在某些**设计文档散文**里写过「大组 = 程序 / 电路 / 机械」。
- **唯一冲突点 = 收敛任务**：当前 `grp-program` 还**直接持有** `t-r1-integration`（R1 总联调）、`t-r2-integration`（R2 总联调），并有自己的成员 `m-progA`/`m-progB`。这跟「程序纯抽象、只四个组领任务」有张力。D-029 原设计允许「收敛任务（如总联调，跨小组）挂大组」。**待用户拍板**（见 §6 待定 #1）：总联调究竟①保持挂在程序大组（作为受认可的"收敛任务"例外），还是②改挂某个叶子组 / 建一个独立的"联调"叶子组。本轮不改 fixtures。
- **落地**：组织结构规则写进 `AGENTS.md §1`（已随本轮）。fixtures 调和留下一轮（依 §6 #1 的拍板）。

## 2. 表现形式：三视图分工 — 决定 A、I、J

用户的核心洞察：**不是二选一，是按用途分几张图**。

### 2.1 长期 / 全局两视图（项目进度）

**① 依赖流程图（总图）** — 已有 `DepGraphPage`，保持现役角色：
全局看「整盘棋怎么走、谁卡谁」，**「不知道未来怎么走的时候看」**。
*可选增强*：在节点上叠「当前态」颜色（在场=蓝描边、随叫=橙描边、可不来=变灰），让总图也能瞥见此刻状态——**列为可选**，主力短期视图交给接力链（§2.2）。

**② 甘特图（项目进度第二视图）** — **新增，且不去钟点**：
排班的「在场三态」去钟点，但**项目整体进度**这件事有合理的时间维度（里程碑 / 赛季节点 / 各机构进度条），所以甘特图作为**和依赖流程图并列的第二个项目进度视图**保留。它回答的是「这个赛季整体推进到哪了」，不是「今晚谁在场」——两个语境别混。
> 这是对上一轮"甘特作废"的修正：**作废的只是"把在场排班画成带钟点甘特"**；项目进度甘特该有。

### 2.2 短期 / 操作视图（在场排班）

**③ 接力顺序链** — 本轮主推的新东西，**支持多车并排**：
把今晚 / 明天每台车的接力顺序画成一条编号链，**只表先后、不表钟点**（直接渲染现有的 `orderInWindow`，彻底不碰时间戳）。给**正在拼装 / 测试**的人一眼看清「现在轮到谁、下一个是谁、我今晚到底来不来」。

```
今晚（顺序，非钟点）             支持多车并排：

26R1  ①电控 ▸ ②机械 ▸ ③视觉      26R1  ①电控 ▸ ②机械 ▸ ③视觉
      在场     随叫     可不来     26R2  ①机械 ▸ ②电控
                                        在场     随叫
```
- 每段标三态颜色（在场 / 随叫 / 可不来）。
- 可叠 D-069 的容量读数 `feasibility`（充裕 / 偏紧 / 冲突）当小徽章——但那是**组级整数**派生，无任何人维度。
- 借鉴：步骤指示器 / 进度链三态规范（已完成实心、进行中脉冲、待进入灰）；on-call 工具的"当前持有→下一个"接替直觉（主键换成组、不换成人）。

**现有卡片网格（`SchedulePage`）降级**：作为接力链点开后的详情，或窄屏退化态；被卡组的「可看资料」收在这里。

### 2.3 加车交互（决定 I、J）

- **排班里的车手动加**；demo 先放两辆：**26R1、26R2**（对应现有 fixtures 的 `res-r1`/`res-r2` + 2026 赛季）。
- 加车的交互形态（**和依赖图一样右上角"加"按钮**，逐个加节点 vs 侧边栏拖拽）= **最后的 GUI 互动优化，先放最后**。先用最简单的右上角加 / 手填即可。

### 2.4 红线自检
三视图的节点都是「任务 / 组 / 车」，颜色来自三态 / 容量派生；没有任何「按人横向计时」的条。"某人这周在场多久"——三视图都答不出。✅

## 3. 资源领域模型：车位 + 具体车 + 零件拆装 — 决定 B、C、D、E、F、H

### 3.1 现状三处缺口（`governance.ts` `SharedResource`）
现在「车」只是一条记录：`{ robotTarget: R1|R2|shared, status: available|inUse|down|upgrading, ... }`。缺：
1. **分不清赛季**——`Season` schema 存在、`Project` 有 `seasonId`，但 `SharedResource` **没有 `seasonId` 外键**；只有「1号车」，区分不了 25R1 / 27R1（明明是两台车）。
2. **状态太少**——没有「在造 / 被拆 / 退役」。
3. **零件来历为零**——「25R1 的电机装到 27R1」无处可记；`InvStore` 是空接口、`INV-BOM-DESIGN` 仍 spec-only。

### 3.2 两层拆分（决定 B）
把混在一起的「车」拆成两个概念（类比：「班长」这个职位 vs「今年的班长张三」）：

- **车位（RobotSlot）**：1号 / 2号这种角色，跨赛季稳定不变。
- **具体某台车（RobotInstance）**：25R1 / 26R1 / 27R1，每台是独立实物，有自己的生命周期和血缘，**永久并存可查**（25R1 退役了，27R1 还要能查它继承了什么）。
  - `displayCode`（25R1）= 赛季后两位 + 车位代号，**派生生成**（禁手写「R1-2025」之类各写各的）。
  - 排班永远挂在「具体某台车」上（`ResourceSession.resourceId → RobotInstance.id`）。

字段草案（实现期细化）：
```
RobotSlot     { id, code: 'R1'|'R2', projectId }           // 车位，稳定
RobotInstance {
  id, slotId, seasonId,                                     // 缺口①补：赛季外键
  displayCode,                                              // '26R1' 派生
  status,                                                   // 缺口②补：见 3.3
  buildStartedAt?, activatedAt?, retiredAt?,
  lineageFromInstanceId?,                                   // 整车继承：27R1.from = 25R1
}
```
**取舍说明**：用户认可拆两层（"其他组每年本来就要做赛季统计，不算额外负担"）。已知最难点 = 「车数据 ↔ 库存零件数据」互联（决定 G 的张力），用户拍板**先做、后期出问题再调**（兜底见 §3.5）。

### 3.3 生命周期状态（决定 C：退役手动）
```
在造 ──激活──▶ 在用 ──┬─撞坏──▶ 故障 ──修好──▶ 在用
                       ├─升级──▶ 升级中 ──完成─▶ 在用
                       └─（手动）退役 ──（可选）拆件──▶ 零件回闲置池
```
- **退役 = 人手动设**，不自动推（守「AI 不拍板」）。
- 退役后两种走向：**整车留着**（展示 / 演示）或 **拆一部分**。
- **状态翻转级联**：某台车翻到「故障 / 被拆 / 退役 / 在造」（= 不可上车），所有依赖它的组自动落「可不来」+ 中性说明（如「25R1 已拆件，今晚无法推进」）。单点翻状态 → 下游整片可不来，是 D-029「车撞坏一翻状态整片下游变 free」语义的自然延续（`schedule.ts` 的 `resourceDown` 分支升级为读「该状态能否上车」）。
- 实现倾向「枚举状态 + 一张行为对照表」（哪个状态能不能排班 / 显不显示 / 要不要告警），不上重型状态机库——状态行为差异小，够用。

### 3.4 零件血缘 + 库存总表（决定 D、E、F）
**「25R1 拆 → 27R1」记成两条动作**（对话记账级，队员一句话、助手代记）：
1. 「把 25R1 的某电机拆下」→ 该零件回到闲置池。
2. 「把它装到 27R1」→ 该零件现属 27R1。
- **关键**：拆件时绝不「删零件再新建」，否则丢掉「这颗电机曾在 25R1」的来历；永远是「拆下」动作让归属变空，零件本身不删。

**粒度（决定 D）**：**绝大多数零件按数量记**（库存里 N 个、某车上 M 个）；只有**1~2 个的、和重要的**（电机 / 电调 / 主控）才单独追踪个体 + 血缘——**做成手动标记**（人勾选"这件要单独追踪"）。

**录入路径（决定 E）**：**初始只录闲置零件数量**（"现在仓库有 N 个 GM6020"）；**每台车上装了多少后续再补**——可由**智能体调接口加**（如读图纸/对话记账派生）或**手动加**。

**库存总表（决定 F）**——回答「闲置多少 / 每台车预留 / 已有多少」：
```
零件          闲置(库存)   25R1   26R1   26R2   27R1(预留)
GM6020 电机       3          2      4      0      6
C620   电调       5          2      4      0      6
主控板            1          1      1      0      1
```
- **不写「在造」列**；写「某台车预留了 / 已有多少个电机」（27R1 列 = 预留数）。
- 退役车若拆，拆下的从「该车列」挪到「闲置列」。
- **拆下的零件进库存总表、不进任务总图**（任务总图只画活儿的依赖）。

> 这套「零件类型 + 零件个体（仅追踪件）+ 拆装动作 + 数量账」正好就是第三支柱**库存 / BOM**（`INV-BOM-DESIGN`）的最小内核——血缘讨论顺手把库存地基摸出来了。本轮**不落代码**。

### 3.5 车↔库存互联兜底（决定 H）
两套数据靠「这颗零件 / 这批数量现属哪台车」打通。**互联出问题时**（数量对不上、血缘断链、孤儿零件）→ **让智能体发消息（走 Hermes / 飞书触点）+ 查问题根源**，而不是默默吞掉或硬卡。这与 AGENTS「AI 当转译 / 仓管、人在环」一致，且对接 `HUB-HERMES-ADAPTER`（仍 gated）。

### 3.6 红线自检
零件、拆装动作、数量账的主键都是物 / 事；记录人只到「谁录的」这种来源（`statusSource`/actor），不做「谁拆了多少件」的人维度统计。✅

## 4. 工作流抽象 + 规范

**两层抽象**：
- **长期主轴层**（赛季尺度，主键 = 具体某台车）：在造 → 在用 → 调试 / 比赛 → 赛后拆件 → 下赛季重建。
- **短期补充层**（今晚 / 本周，主键 = 组）：在场排班，挂在主轴「当前可用的车」上。正是用户说的「流程图的短期补充」——覆在长期图上的一层薄运行态，不是独立日历。

**该标准化（少数硬规则，否则数据散乱）**：车 `displayCode` 派生生成（禁手写）；状态迁移走写入白名单（沿 `GovStore` 白名单），AI 只出建议、人确认才落；拆件固定记两条动作、备注必填，记错用「修正」动作不删历史。

**该保持轻量（别建没人填的死表格，守 P13）**：不强制录设计图纸级 BOM（留 CAD，只在用到时挂模板）；不强制每颗螺丝编号（只追踪贵重件，决定 D）；排班不强制提前排满（谁在推就标谁，是建议草稿不是考勤表）；在场三态不引钟点。
