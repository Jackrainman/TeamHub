## 1. 意义

> 把战队“谁在做什么、卡在哪、谁太忙 / 谁在干等”从**凭感觉 / 因信称义**变成**直观可查的事实**；当有人卡住、或有隐含依赖没人去满足、或新人不敢开口时，由系统**以“帮忙”的姿态（而非监视）替他暴露并促成那一步协作**。

痛点来源（用户实证）：

- 工作以**线下交流为主**、聊天在微信、线上数据天然稀薄；上一次推广（学长尝试用飞书）**死于上手难度**。
- 典型拖延：视觉以为任务完成 → 与电控联调炸了 → 视觉没有主观能动性去找电控要测试板 → 拖几天。**真正的痛点不是“任务慢了”，而是“有一个没人去满足的协作需求 / 隐含依赖”**，且当事人没意识到 / 不好意思 / 不知道。
- “不敢说 / 不敢找学长要东西”的心理**主要在大一**，大二 / 大三较少。

## 2. 五条不可动摇的原则

1. **系统是大脑，飞书是脸**：任务 / 人 / 依赖的真相在系统（关系型库）；飞书只做汇报出口、通知、一键 check-in、给老师的自动汇报；微信继续当聊天。**不双写**（同一件活不会既在飞书干又在系统填）。
2. **不新增日常录入义务**：录入主体是**队长 / 组长布置任务那一刻**（一次性录参与人 / 角色 / 跨组依赖）；进度靠 Git 信号 + 轻 check-in + 沉默检测**自动派生**。
3. **暴露需求，不暴露人**：永远说“这条链缺测试板”，绝不说“E 慢了”。**无人效排名 / 绩效分 / 贡献榜**（宪法 #2）。
4. **无硬截止，只有轻提醒**：不设 deadline；沉默几天 → 一条**可一键回**（在忙 / 不太会 / 缺个东西 / 正常推进中）的帮忙式提醒；系统不猜原因。
5. **助手不是监视**：系统给得比拿得多（AI 知识 + 帮你找对人 + 替你开口），才换来观察你的资格。

## 3. 核心数据模型（数据真相层）

```text
赛季 Season ── 顶层容器（RoboCon 每年新车 = 新图；人员 / 经验跨赛季沉淀）
组 Group ───── 可配置组织树（机械 / 电路 / 程序{电控, 视觉}，合并 = 改配置，不改代码）
队员 Member ── {角色: super_admin(队长/维护者) | 组长 | 队员, 主组, 可跨组, 年级/资历}
任务 Task ──── {赛季, 牵头组 = 重心所在组, 状态, 规模, 软周期“本周/本阶段”, 最近活动时间}
   ├─ 参与 Assignment {角色: 主负责 | 协作 | 技术支持}   ← 跨组“自然掉出来”：参与人.组 ≠ 牵头组
   ├─ 前置需求 Need {描述, 提供方(组/人), 状态: 待满足/已满足}  ← 人填 / AI 建议 / 本人确认；治“我以为”
   ├─ 依赖 Dependency → 任务（人工连线，A 等 B）
   └─ 用到 → 资源 Resource（今年新板 / 去年车 …；可争用）
信号 Signal ── {任务, 类型: commit | check-in | 状态变更, 时间}  ← 派生，喂规则层
```

设计要点：

- **任务 ↔ 人 是多对多 + 带角色**（主负责 / 协作 / 技术支持），这是把“因信称义”变“一张可查的表”的核心；关系型库自然，bitable 别扭（故飞书不当数据层）。
- **牵头组 = 任务重心所在的组**，不一定是发起者那组。例：“电控 A 和机械 B 联调模块 a”→ 牵头组 = **机械**（因为要测试效果），A（电控）是协作。
- **跨组技术支持**= `参与.角色 = 技术支持` 且 `参与人.组 ≠ 牵头组`，模型天然表达，无需单独“跨组”概念。
- **前置需求 Need** 是“协作缺口”的载体，也是中央视图上会亮红的点。

## 4. 魂 · 中央视图 = 动态依赖图（务实版）

愿景为用户提出的“动态最短任务周期图”（项目网络图 / 关键路径，化工流程图的工程版）：

```text
节点 = 任务（谁 · 什么组 · 状态）
边   = 依赖（含 AI / 人 补出来的隐含依赖，如“联调 ← 电控出测试板”）
目标 = 让“最长的那条链”和“链上的红点”无处可藏
动态 = 任务完成 / 卡住 / 新依赖浮现时，图自动重算
```

落地分两档（已拍板：**先做务实版**）：

| | 务实版（先做） | 完整 CPM（留位、未必做） |
|---|---|---|
| 靠什么高亮 | **结构 + 状态**：阻塞链全亮红 / 收敛点（总联调等高汇入）预警 / 长链重点盯 | 工期数值算精确最短周期 |
| 要不要工期 | **不要** | 要（违背“低录入”） |
| 抓痛点 | 能（哪条链卡了、谁在假完成、谁在干等） | 更精确，成本高 |

围绕中央视图的三个判定（规则 / 治理层，全程不靠人主动开口、不靠感觉）：

1. **卡住**：任务连续 N 天无任何信号 → 标「疑似卡住」→ 轻提醒（系统替羞于开口的人说话）。
2. **过载**：某人在手「主负责」任务超阈值 → 标「过载，建议分流」（只说“太忙”，绝不排名）。
3. **链路阻塞 / 假完成**：标了“完成”但有下游联调边 → 提示“端到端真验过了吗？下游在等你”；上游卡 → 下游全链亮红。

让所有人动起来：**过载**（太忙→分流）与**干等**（在等卡住的上游→建议并行 / 搭把手）是一体两面，措辞均为帮忙。

对**大一**更主动兜底、更鼓励、“替你说”权重更高；对学长轻触——中央视图与提醒共同构成**给新人的安全网**。

## 5. 反“监视感”的四条机制

1. **暴露“需求 / 缺口”，不暴露“人慢了”**（= 宪法 #2）。
2. **提醒先私下给本人、帮忙口吻**；老师 / 全队只看**项目级进度**（车做到哪了），不看个人；组长能看本组缺口（“任务缺 X”而非“人慢”）。
3. **系统给得比拿得多**：观察是为了回馈帮助，这是不令人反感的根本。
4. **无 deadline 只轻推**；轻提醒可一键回，既帮人又便宜地拿到信号，还不用系统猜原因。

（用户想要的“结合课表更人性化”= 机制 2/4 的延伸：考试周 / 上课时段不打扰。**先设计进模型，暂不实现**，控制复杂度。）

## 6. 边界与四层架构

- 飞书集成需**固定 IP**（无服务器 / 动态 IP 不可用，见 `docs/research/lark-api-capability.md` §4.1）→ 飞书集成 + Forgejo 都归宿到**固定 IP 的战队服务器**（当前几乎闲置，让它发挥价值）。WSL2 开发机仅做演练。
- Git：战队服务器自托管 **Forgejo**（解决团队“GitHub 常推不上去”）+ 镜像回 GitHub（备份 / 对外）；与 D-025 §3.4「Forgejo 默认」一致，价值定位从“只索引”升级为“给战队一个能推得上去的远端 + Hub 索引它”。
- bitable 关系能力弱 / QPS 低 / 有写冲突，且“上手难度”是上次推广失败主因，**故不当数据层**（见 §2 原则 1）。
- **四层架构（每层只依赖下层，这是“逻辑不缠成一团”的关键）**：

```text
触点 / 集成层   飞书 I/O · Git webhook · 机器人          ← 可换可加，不碰核心
展示 / 汇报层   控制台中央依赖图 · 给老师的汇报视图       ← 只渲染，无业务逻辑
规则 / 治理层   卡点 · 过载 · 干等 · 假完成 · 升级规则    ← 读真相，发信号（产品的魂）
数据真相层     组织树 · 任务 × 人 × 依赖 · 需求 · 资源   ← 稳定内核
```

## 7. 已定 vs 待定

**已定**：产品意义 / 形式、系统是大脑·飞书是脸、核心数据模型、魂（隐含依赖暴露）、中央视图务实版、年级安全网、无截止只轻推、反监视四原则、Git = 自托管 Forgejo。

**待定（后续逐条拍板，升本文件 / D-026 至 stable）**：

1. **角色权限细则**：各角色（super admin / 组长 / 队员 / 年级）能看 / 能改什么，× 如何与“不监视”原则一致。
2. **提醒触发规则**：沉默阈值、依赖链联动亮红、轻提醒一键回应的具体语义。
3. **AI 边界**：只建议依赖 / 需求，还是兼做知识问答 / 提醒措辞；如何不越过“助手”变“监视”。
4. **提醒可见范围**：用户倾向“混合”，仍在斟酌（候选：缺口任务级对相关方可见、“该你动了”私聊本人、老师看项目级）。
