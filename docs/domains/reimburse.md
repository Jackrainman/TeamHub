# Reimburse 领域

## 1. 职责与边界

Reimburse 管采购/费用条目、发票元数据、材料清单、报销批次、付款/查验状态和入库关联。票据解析始终在浏览器本地运行；凭证原件按 D-094 走受控留档通道（后端已落地，前端入口与随批次打包见 §7）。

## 2. 当前行为（CURRENT）

- 支持 goods/expense 条目、材料 checklist、批次状态和基于分单位整数的金额。
- 控制台以表格呈现获授权条目，按派生状态筛选并选择导出 CSV；录入、导入确认、条目详情与财务管理使用抽屉。关闭导入确认保留待确认票据，明确跳过或保存才推进队列。
- 浏览器用 pdf.js 读取 PDF 文字层，也可解析电子发票 XML；纯扫描件无法识别时回到手填。
- `unitPriceFen=null` 表示单价无法精确到整分，不得硬凑；quantity 可为小数。
- 身份模式下 API 按本人/项目管理员可见性返回条目和批次，发票号查重；匿名模式没有个人边界，会返回全量条目。
- goods 条目通过窄 stock-in context 选择库存候选；服务端在同一 SQLite UnitOfWork 内写结构化 `reimburseItemIndex`，前端不读完整库存或解析 note。
- PDF/XML 会保留购买方名称、税号和识别来源；部署级 profile 默认校验哈尔滨工业大学抬头，双空值可跳过。
- 卡片显式区分“需换抬头”和“需核对”，给出归档命名建议；批次按 gross/eligible/blocked/review 展示，blocked 条目阻止提交。
- 归档导入已落地（REIMBURSE-OFD-PARSE v0.59.0）：ZIP 解包队列 + OFD 内嵌 XBRL（铁路客票真实样本 4/4 通过），统一安全门（输入 50MB/条目 200/解压总量 200MB/嵌套不展开），包内发票号去重留结构化源；尚无 OCR 和真正的文件筛选下载导出。
- 凭证受控留档通道已落地（REIMBURSE-EVIDENCE-STORE）：条目级 `POST/GET/DELETE /api/reimburse/entries/:id/evidence[/:evidenceId]` 与 `.../download`、`.../evidence-downloads`；只收 PDF/PNG/JPG（单文件 20MB、单条目 12 份），字节落 `TEAMHUB_EVIDENCE_FILES_DIR` 本地卷（原子写 tmp→rename），库内 `reimburse_entries.evidence` 只留元数据指针（含 sha256）。上传只认条目本人（超管不得代传），下载/删除/留痕走「本人→超管」读者链且每次成功下载记一条 `reimburse_evidence_downloads`；批次提交后快照锁同样锁凭证。前端入口在条目卡片的「凭证留档」区（`ReimburseEvidenceSection`）：收起时零请求，展开才取清单；后缀/大小在浏览器按 contracts 同一口径预检，下载是 cookie 鉴权的 `<a download>`（无静态路径）。

## 3. 目标结构（TARGET）

- 已冻结首个三包同构模板；后续只在域内扩展 parser、export adapter 和窄跨域 port。
- 统一归档安全门已落地（contracts planInvoiceArchive + console archive-extract）；OCR 只有真实样本验证达标后才允许进入本地 import pipeline。
- CSV 条目选择导出已落地；凭证留档的受控附件通道已按 D-094 建好（鉴权上传 + 下载留痕），剩「随批次打包交财务」一节；解析始终留浏览器。

## 4. 领域不变式

- 票据解析（PDF/XML/ZIP/OFD）与 OCR 始终在浏览器本地运行；服务器不装票据解析依赖——它的 multipart 入口只做凭证字节的搬运与留档，不读内容、不识别（D-094 拆分后 ① 不变、② 作废）。
- 凭证附件（发票/付款截图/查验单原件）是**条目级私有事实**：只对提交本人与承担财务职责的成员（沿用超管/PM 旗）可读，永不进列表、聚合、统计或无鉴权静态路径，下载留痕。落地上表现为：条目对象出 HTTP 前 `evidence` 一律剥成空数组，原件清单只经 `GET /entries/:id/evidence` 流动，字节只经鉴权 `.../download` 流出。
- 金额以分为整数；不能精确表达时显式标记需核对，不制造小数精度。
- 条目人键只回本人和项目管理员；批次聚合无按报销人明细或统计。
- 抬头不匹配、信息缺失和人工/OCR 补录必须给结构化核对原因。
- AI/OCR 结果是草稿，用户确认后才进入正式条目。

## 5. 跨域接口

- inventory 只暴露零件匹配和 stock-in port；报销不读取库存完整 snapshot。
- system 通过 `AppSettings.projectId` 提供项目上下文；报销 profile 由本域 singleton repository 持有。
- 本地 import pipeline 复用统一归档安全门；导出使用共享 export/filename 基础设施。
- PM 可查看有权限的报销事实和导出，但名字不得进入治理聚合。

## 6. 已知陷阱

- profile 变更会重新派生历史条目的质量状态；这是部署标准变化的显式结果，不能静默固化旧判断。
- `recognitionSource=manual/ocr` 即使字段齐全仍会进入“需核对”，避免把草稿识别当成已验证事实。
- 纯扫描 PDF 文字层为空时只能手填；OCR 技术可行性尚未用真实样本验证。

## 8. 第一版材料包导入设计（TARGET，2026-11-04）

本节是待实现设计，不代表 §2 的当前行为。实现计划唯一记录在 `.harness/todo.json` 的 `REIMBURSE-PACKAGE-V1`。用户已确认导入单位；真实样本待用户整理后提供，OCR 验收不得用合成样本代替。

### 8.1 目标与方案选择

- 一件报销事对应一个顶层 ZIP，内容为一张发票及付款截图等配套材料；一张独立 JPG/JPEG 也对应一个条目。多份散图由用户先打成 ZIP；批量选三个文件就产生三个独立确认项。
- 采用用户选择的「按顶层文件分组」方案：边界由提交人决定，系统不猜配对。原有「ZIP 内按每张发票拆项」不符合这一规则；跨散图自动配对容易把不同支出混在一起，第一版不建设。
- 保留已有单 PDF/XML/OFD 导入入口；PNG 可作为 ZIP 内附件。ZIP 内同一张发票的 PDF/XML/OFD 多格式只算一张，优先结构化源；发现两个不同发票号时保持该包为一个冲突项，要求用户整理，不偷偷拆项或求和。
- 此次不改库存业务、不做批次附件导出、不改任务池/备位池/任务验收。周任务继续沿用历史关联和最新状态查询。

### 8.2 用户流程

1. 本人批量选择 ZIP/JPG（或已有票据格式），浏览器逐包解压、读取文字和识别，显示处理进度；单包错误不阻断其他文件。
2. 每个包进入一个确认草稿，显示原文件名、识别来源、票据类型、发票字段和包内附件列表。附件候选角色为发票、付款凭证、查验单、待分类；用户可改分类或明确排除文件。
3. 分开显示「材料未发现」「字段未识别」「需人工核对」。未识别不等于原件没有，付款截图也不能冒充发票。材料提示默认要求发票与付款凭证；查验单是否已备沿用现有自证规则，不因上传图片自动勾选。
4. 用户核对后保存，可保留信息不完整的条目并稍后补齐。未知金额保留 null，显示「未填写」，不预填 0；统计仅合计已知金额并提示存在金额待补条目，缺金额条目不能装作完整或进入可提交金额。
5. 保存条目后，将确认纳入的附件经现有受控端点留档。界面分别反馈「条目已保存」「附件已保存/待重试」，不得把解析成功说成留档成功。
6. 附件失败时保留条目 ID 与未完成附件，重试只补传；关闭抽屉不丢确认内容。刷新会丢失尚未上传的本地 File，需明确提示重新选择原包，不能承诺后台继续。相同条目内相同内容与角色的重复上传须幂等。
7. 已保存且尚未锁定的本人条目可补改核心字段；批次提交后沿用冻结规则。库存已关联的条目不能改类型或明细索引/数量等影响既有入库事实的字段。

### 8.3 识别与核对规则

- 先用 XML/XBRL/PDF 文字层；图片及无文字层 PDF 才进入浏览器本地 OCR。Worker 和语言资源按需加载，失败或超时回到人工填写，取消后释放资源；服务器不识别票据，不接外部 OCR 服务。
- 票种第一版为 `vatOrdinary`（普通发票）、`vatSpecial`（专用发票）、`railway`（铁路客票）、`other`（其他明确票种）、`unknown`（待确认）。这是票据种类，不等同于采购/费用分类，也不是税务真伪查验。无可靠依据保持 unknown，允许本人修正。
- 字段核对包含号码、日期、销售方、金额、按配置要求的抬头/税号及采购明细；继续复用 contracts 的金额与抬头规则。OCR 来源保持可见，人工确认不把来源改成 PDF/XML。
- 付款成功、交易单号等文字只能辅助附件分类，不能直接生成发票字段；文件名只提供待确认建议。重复发票、多票、不同来源金额冲突、金额与明细不一致都显式提示。
- 继续执行现有 ZIP 限制：输入 50MB、条目 200、解压总量 200MB、嵌套容器不展开。加密/损坏/不支持文件明确列出；同名成员不得静默覆盖。附件仍受每份 20MB、每条目 12 份限制，超出时让用户选择，不静默截断。
- 新入口中的原件范围为 PDF/PNG/JPG；现有可解析的 XML/OFD 原件拟扩展为受控附件白名单，服务器只存字节、鉴权下载，不解析或内联执行。ZIP 容器本身不上传；包内其他格式列为未纳入材料，不伪装成已归档。

### 8.4 状态、权限与工程边界

- 条目就绪状态（草稿/待补充/齐全）、识别核对状态、原件留档状态、批次状态四者分开，不能因为有文件就标成齐全或已报销。
- 新增票种与未知金额语义属于报销契约；用户修正须通过同域 service 校验、发票号查重和 SQLite 持久化。附件文件名、内容散列、OCR 原文、下载记录不进入普通列表或聚合。
- 普通成员只处理本人条目；财务沿用现有管理员旗与受控阅读范围。上传仍只允许本人，任何新入口都不绕开已有鉴权、批次锁或凭证下载留痕。
- 保留当前预期版 UI 的表格、状态筛选、选择导出和侧抽屉，在导入确认抽屉中增加识别结果、缺项和附件确认，不另建第二套报销页面。
- 真实样本不得进 Git、公共截图或外部识别服务。OCR 样本覆盖票据照片、付款截图、带文字层 PDF、纯扫描 PDF、同票多格式 ZIP、多票冲突 ZIP、缺材料和不清晰图片；记录字段命中/误识别、耗时和内存后决定是否达到上线条件。

- 原型中的导入是页面内存演示，状态标签、凭证图标与库存加减也不是完整业务承诺。主项目保留既有权限、批次和库存账本语义；不能把 UI 已合入等同于 OCR 与按包留档已实现。
