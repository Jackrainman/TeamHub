## 二、命名决策：「知识库」→「排障档案」

**问题**：战队已有文档站记录知识点（"怎么做的"），TeamHub 的 KB 模块实际数据 = IssueCard + ErrorEntry + 调查时间线（"坏了什么、怎么修的"），两者撞名。

**决策**：
- TeamHub 原「知识库」页面 → 改名 **「排障档案」**（Debug Archive / Troubleshooting Archive）
- 图纸档案不动
- 向导 KB 步 → 改为「导入排障笔记 .md」
- 边界：排障档案 = 时间线叙事（什么时候坏、查了什么、结论）；文档站 = 参考手册（怎么做的）；图纸档案 = 版本化交付物

**落地范围**：console 导航标签 + i18n + 向导步标题。不改 contracts schema 名（内部仍叫 kb，只改用户可见文案）。

### 第二步：Hermes 最小链路接通（体验修复之后）

**定位（2026-07-25 讨论拍板）**：Hermes = **飞书侧薄壳遥控器**，不是「AI 自动化流程」。
- 价值 = 把 TeamHub 已有 API 的入口搬到飞书群（@bot 查库存 / 一句话快记 / 推通知）
- 不做 = 听对话自动记账（已判死，inv-alert-redesign §1）/ AI 解析群聊派生状态（治理冻结）
- 意义不是设计出来的，是接上之后用出来的。先通管子，再炼 skill，没人用的不建。

**Hermes vs OpenClaw**：当前体量使用上一样。Hermes 已接飞书已跑着，先用它通路。OpenClaw 架构可能更适合「多 skill 遥控器」，但迁移成本不大（TeamHub 侧接口不变）。不急着换。

**最小链路**：
| 步 | 谁做 | 内容 |
|----|------|------|
| 2a | TeamHub | `POST /api/hermes/inbound`：接收 `{command, args}` → 调已有 API → 返回结果文本 |
| 2b | TeamHub | 第一个 command = `inv-query`（查库存）+ `inv-record`（一句话快记） |
| 2c | 用户 | Hermes 侧写 skill：解析飞书 @消息 → 调 2a → 回复发回飞书 |
| 2d | 用户 | 飞书群 @bot 试一条，通了就完事 |

**验证策略**：
1. contracts 定接口（纯类型，不碰网络）
2. server 写实现 + 本地单测覆盖 95%（mock transport，`npm test` 全绿即放心）
3. 集成 smoke = 一条 curl / 一条飞书消息，不需要写测试框架

## 四、产品判断备忘（2026-07-25 讨论）

**什么是对的**：
- 项管看板 + 基准线倒排 + 库存台账 = 日常真用（结构化、不需额外记录）
- 降低组间摩擦靠人坐近一点、学长多学多带，不靠 AI 当桥梁
- .debug_archive = 攒经验阶段的个人工具，不推广、不强制、留着支援未来
- KB/排障档案的价值在人员更替时显现（下届翻上赛季坑），定位 = 赛季末结案归档处

**什么是伪命题**：
- 指望人日常对 bot 汇报 → 饿死（已判死）
- 为了「攒经验」强制记录 → 负担，没人做
- 小问题现场解决不走 AI → archive 天然稀疏，这是正常的
- 在没接通之前设计 10 个 Hermes skill → 为了做而做

**原则**：不做就不知道有没有问题。最小链路接通 → 发现真实场景 → 再炼对应 skill。
