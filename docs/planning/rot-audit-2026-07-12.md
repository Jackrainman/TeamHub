## 第一部分 · 防石山优化清单

六个维度共查出 20 多条，经对抗核实后：4 条被推翻剔除（见文末），其余按紧迫度分三档。**每条都已确认不碰红线**（不给任务加截止日期、不点名谁慢、不把登录密码写进日志、旧数据仍能读、SQLite 仍是选配）。

### 🔴 现在就做（3 条，都是“安全网有洞”，拖着就是赌运气）

**1. 三套数据存储没有“同一张卷子”，新上的 SQLite 后端可能悄悄算出不一样的结果**
- 问题：任务/依赖等数据有三种存法（内存版、文件版、新的 SQLite 版）。规矩要求三者行为必须一模一样，但目前是各写各的一份、各考各的试卷，没有一张卷子同时考三个。
- 再拖会烂：SQLite 版是你之后可能切换成默认的存储方式。今天靠“人记得三处一起改”撑着，只要有人改了一处忘了另一处，SQLite 那份会**在没有任何报错的情况下**跟其它两份产生分歧，等发现时数据已经不对。
- 修法：写一份“统一契约测试”，让三种存法都跑同一批断言，任何一处对不上立刻测试变红。
- 工作量 **L** · now.md 未登记。（注：核实时发现文件版其实是“借用”内存版、天然不会跑偏，真正会跑偏的是内存版 vs SQLite 版这一对，问题范围比原报告略小，但结论不变。）

**2. 程序的真正启动入口从没被“真刀真枪启动过一次”测试，包括一条出过事故的安全防线**
- 问题：程序主入口里有几条按环境开关走的岔路——其中一条是安全铁律：**对外网开放却没配写入口令时，必须拒绝启动**。这条防线过去真的裸奔过一次（有事故记录）。但现有测试都绕过了主入口，这几条岔路从没被真实启动流程跑过。
- 再拖会烂：这正是历史上两次“接线漏了”事故（安全防线、模块开关）的同一个根因。第三次再漏，没有任何自动流程能拦住，只能靠人再审一遍才发现。
- 修法：加几个“真的把程序启动起来”的测试：故意不配口令+对外开放 → 断言程序拒绝启动；开 SQLite 启动一次 → 断言数据能存能读、重启不丢；开模块开关 → 断言被关的功能确实访问不到。
- 工作量 **M** · now.md 未登记。

**3. 备份脚本只备份两份老数据，新加的三份数据在裸奔**
- 问题：备份脚本只备 `kb.json`（知识库）和 `gov.json`（任务治理）两份。但 7 月新加的三份数据——库存台账、倒排基准线（含验收过门留痕）、接力排班窗口——一份都没进备份。安全铁律的文字也还停在“只有这两份不可再生”，跟实际数据面脱节了。
- 再拖会烂：谁哪天照规矩“重启前先备份”，会在磁盘上留下一份**看着完整、其实缺了基准线和库存**的假备份。真出事回滚时才发现少东西。
- 修法：备份脚本补上那三份的备份调用（SQLite 直接整文件复制），并把安全铁律的文字改成指向真实的数据文件清单。
- 工作量 **S** · now.md 未登记。

## 第二部分 · 发布链路一页纸（v1.0）

> 核心结论先说：**功能层零欠债，距 1.0 只差一个“打包 + 一次干净装验证”的小冲刺，不需要任何新功能开发。** 真机上线是审批后的另一条独立轨，不阻塞“发布物就绪”。

### 一、什么时候配叫 1.0（放行判据 / gate 清单）

先分清两件事：**“切一个 1.0 安装包”**（打标签+产出压缩包，不碰服务器、随时能做）vs **“部署到战队服务器”**（卡审批门）。判据只管前者。

**必须做完才配叫 1.0：**
- ✅ 三支柱 + 路线 v4 四刀功能——已闭环，三包测试全绿。
- ❌ **离线安装包存在且验证过**（在一台干净机器上从零装通）——**这是唯一真正的阻塞，是打包活不是功能活**。
- ⚠️ **一次冷启动走查**：空板模式起服、9 页零错、建任务→重启→还在（证明落盘真接通）。
- ❌ README 去掉“还在建/v0.3 冻结”这类字样，改成 1.0 口径。
- ⏳ **待你拍板**：默认主题（tech 风）和学习方向 3D 星图这两个界面项，保留还是撤——留=什么都不做，撤=各回退一刀。门面不能带着“还没定”的东西发。

**明确不挡发布：** 真机上线（卡审批，属发布后动作）、库存/知识库仍用 JSON 没迁 SQLite（有意的边界）、飞书/Hermes 真实接入（本就“最后做”）、游戏工作室包、治理 AI（主动退出）。

### 二、发布在哪 / 版本怎么切

- 版本 **0.17.0 → 1.0.0**：用现成脚本 `bump-version.sh major` 一次推齐所有包（**别手改 package.json**，那是历史 bug 根因）。
- 打**仓库第一个 git 标签 `v1.0.0`**（现在零标签）。**待拍板**：现在就打，还是先把压缩包验证过再打。
- GitHub Release 挂三样：**离线压缩包 `teamhub-1.0.0.tar.gz`** + **校验和 `.sha256`** + GitHub 自带源码包。
- **不发 npm**（内部私有包，不是给人装的库）、**docker 只留作可选**（离线搬镜像还要装 docker，不如直接给压缩包轻）。

### 三、怎么打包（推荐结论 + 一句为什么）

**推荐“预构建压缩包”**（把编译好的产物+运行依赖一起打进去，落地即跑）。
**一句为什么：** 实验室可能断网是硬约束，“现场装依赖”方案直接出局；而本项目运行依赖全是纯 JS、无需重新编译，打好的包拷到任何 `node≥24` 的机器落地即跑，升级就是换包解压。仓库现成的 Dockerfile 已经算好了“最小运行时集合”，打包脚本照抄即可。
**待拍板：** 要不要把 node 程序本身也打进包里？打进去=目标机连 node 都不用装（更省心），代价是包大几十 MB。战队服务器就一台、架构固定，建议打一份对应架构的进去。

### 四、安装五步（队友视角）

1. **拿到文件** `teamhub-1.0.0.tar.gz`（U 盘/内网/SSH 传均可）。
2. **核对没坏** `sha256sum -c teamhub-1.0.0.tar.gz.sha256`。
3. **解压** `tar xzf teamhub-1.0.0.tar.gz`。
4. **一键装** `cd teamhub-1.0.0 && ./install.sh`——它会：查 node 版本、建好数据目录（**已存在则绝不覆盖**）、交互问四件事（只本机还是全队内网→决定是否自动生成写入口令；匿名还是登录模式；空板还是演示数据），然后起服。
5. **浏览器打开** 屏幕打印的地址（默认 `http://内网IP:4177`）。完。

### 五、升级两步（核心原则：代码目录整个换，数据目录永不动）

1. **先自动备份**（安全铁律）：`backup-teamhub-data.sh` 会带时间戳快照并**读回校验**，校验不过就停手别升级。（这一步塞进 install.sh 的升级分支，不靠人记性。）
2. **换新目录起服**：新压缩包解压到**新目录**（旧目录留着回滚），数据文件路径仍指向同一份 `~/teamhub-data`，停旧起新，再 `curl /health` 确认换上的是新构建、老数据还在。

> 回滚：旧代码目录还在→停新起旧即可；数据从备份目录拷回。
> 两个迁移例外：6 月前的老 `gov.json` 升级前先跑一次兼容迁移脚本；开了 SQLite 才涉及 SQLite 迁移。其余 JSON 天然向后兼容。

### 六、repo 需要新增的文件（4 个）

- **`scripts/release.sh`** — 干净编译三包→按 Dockerfile 逻辑收拢最小运行时→打成压缩包+生成校验和。
- **`install.sh`**（打进压缩包）— 查 node、初始化并保留数据目录、交互写配置、升级分支自动备份、跳过编译起服。
- **`INSTALL.md`** — 队友视角的傻瓜版安装/升级/回滚说明。
- **`CHANGELOG.md`** — 1.0.0 版本记录。

**复用现成、不用新写：** `start-teamhub.sh`（走跳过编译）、`backup-teamhub-data.sh`（升级前备份）、`bump-version.sh`（切版本）、迁移脚本、Dockerfile（当运行时集合蓝图）。

4. **真机部署到战队服务器**（写 systemd 自启、开机常驻、反代/口令配置）——卡 §5 审批门，属发布后的独立轨，**必须你白天审批后才动**，不阻塞安装包就绪。
